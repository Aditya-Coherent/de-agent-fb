==================================================================
This is a from-scratch explanation of the whole system, not just a
changelog. Read top to bottom if you (or your mentor/tech lead) need
the full picture in one place.

------------------------------------------------------------------
1. WHAT THIS PROJECT ACTUALLY DOES
------------------------------------------------------------------
Given a market name (e.g. "Global Avocado Oil Market"), the system
produces a full market-sizing workbook: total market value, split by
country/region, split by product segment, priced per product, for
years 2021-2033. This is the same kind of output a human market
research analyst would hand-build in Excel over days/weeks -- the
goal here is to generate a first-draft version of it automatically.

There are TWO separate ways the system arrives at a number for the
same market -- built independently, on purpose, so they can be
checked against each other:

  DEMAND-SIDE   -- "top-down": start from world/market knowledge,
                   narrow down with real evidence.
  SUPPLY-SIDE   -- "bottom-up": start from real numbers (either real
                   companies' revenue, or real published figures) and
                   add them up. ("Bottom-up" and "supply-side" are the
                   same thing -- bottom-up is the technique, supply-
                   side is the resulting number.)

Two completely different outputs are also produced downstream of the
demand-side number:
  INPUT SHEET   -- the raw sized-and-segmented numbers (what the
                   demand-side pipeline directly produces).
  ME WORKBOOK   -- a second, separate pipeline that takes the Input
                   Sheet and re-derives a full year-by-year workbook
                   (Market Value / ASP / Market Volume, per geography)
                   through its OWN agents -- not a copy of the Input
                   Sheet's numbers. The two will differ slightly by
                   design (confirmed real example: Input Sheet said
                   $748.3M for Avocado Oil 2026, the ME workbook
                   independently landed at $792.76M, ~6% apart).

------------------------------------------------------------------
2. DEMAND-SIDE PIPELINE (src/me_engine/generation/)
------------------------------------------------------------------
Entry points: backend/main.py (`/api/generate` SSE endpoint, used by
the Next.js UI) and the underlying LangGraph graph in agents.py.

Flow (LangGraph StateGraph, nodes run in this order):
  structure_node   -> checks our own Neon DB for a past report on
                       this exact market (keyword match, then a
                       SEPARATE verification step using an LLM call
                       to confirm the match is real, not just similar-
                       sounding -- retries with a meaning-based/
                       semantic DB search if the keyword match fails
                       verification). ALSO, independently and always
                       (regardless of DB match), runs 3 live web
                       searches (ddgs library) for size/forecast,
                       regional split, segments/pricing, PLUS extra
                       per-category web searches for every dimension
                       (measured to matter: segment splits are where
                       the AI is worst without category-specific
                       evidence).
  market_size_node -> LLM drafts global 2026 value + CAGR from all
                       gathered evidence. Real-data-grounded rule:
                       if the evidence contains an EXPLICITLY CITED
                       figure, the LLM's number must match it, and a
                       CODE-LEVEL regex check (_extract_cited_value_mn)
                       auto-corrects the LLM's number if it doesn't
                       line up (real bug found+fixed: AI confused
                       "$214 billion" with "$214 million" -- code now
                       catches this every time, not just via a prompt
                       instruction). If NO explicit figure exists in
                       evidence, still produces a best estimate but
                       tags it "ungrounded" (grounded=false) so this
                       is tracked honestly instead of hidden.
  geo_node / shares_node -> splits the total by country and by
                       segment dimension, using the per-category web
                       evidence gathered in structure_node.
  asp_node          -> sets a price per product.
  reward_node       -> a SEPARATE LLM call grades the whole draft for
                       consistency + plausibility. If the score is
                       weak, the loop redoes market_size/geo/shares/asp
                       and scores again -- up to 4 passes (min 2).
                       Always keeps the BEST-scoring pass across all
                       attempts, not just the last one tried.
  finalize_node     -> restores the best pass, computes quality flags
                       (see section 5), writes output.

Output: an Input Sheet .xlsx in agentGeneratedInputSheet/, plus a
line in output/generation_history.jsonl.

KNOWN LIMITATION: structure_node only works if the Neon DB has SOME
report to search (even a distant semantic match) OR web search is
enabled. If a market has zero DB coverage and web is off, it can
still run on live web evidence alone -- but demand-side generation as
currently wired via the UI/backend requires source="db" and will
error with "No DB segmentation found" if nothing matches at all in
the DB path specifically. (3 of 5 markets in a batch test -- EV
charging, solar panels, cloud computing -- hit exactly this.)

------------------------------------------------------------------
3. SUPPLY-SIDE / BOTTOM-UP PIPELINE (src/me_engine/supply/)
------------------------------------------------------------------
Entry point: compare_demand_supply.py CLI. Two techniques, selectable
via --method:

  A) EVIDENCE-BASED (evidence_estimator.py) -- DEFAULT method.
     Zero LLM calls anywhere in this path. Steps:
       1. ddgs web search for real market-report content (3 queries).
       2. Embedding-based relevance filter: market name AND every
          search result get converted into a VECTOR (a few hundred
          numbers capturing meaning, via sentence-transformers, same
          model already used for Neon DB semantic search). Results
          whose vector sits too far from the market's vector get
          thrown out -- this is what stops "Popping Candy Market"
          from being counted as the whole "Candy Market".
       3. Regex extraction: pulls out only numbers EXPLICITLY written
          in the text (e.g. "USD 636.3 Million") -- no AI guessing.
       4. Google Trends signal: real public search-interest data,
          nudges the CAGR up/down slightly (small effect, never
          touches the size itself). This replaces the "sentiment
          analysis" idea from the original plan -- podcasts and
          Reddit were both tested and ruled out as free sentiment
          sources for niche B2B markets (podcasts have no real
          coverage; Reddit's new API policy blocked account creation).
       5. Deterministic aggregation: takes the MEDIAN across every
          real figure found. Not an AI's pick.
     No company list needed to run this. Only works when the market
     has some existing public research coverage to find.

  B) COMPANY-BASED (estimator.py, graph.py, financials.py, discovery.py,
     geography.py, verify.py) -- OPT-IN (--method company).
     Sources real companies (via --companies file or --discover, a
     small LLM-based discovery step), then for EACH company:
       - Checks yfinance + InsightSentry (RapidAPI) for real filed
         financial data. If found (PUBLIC company), that real revenue
         HARD-CAPS whatever the LLM estimates -- no guessing allowed
         past that ceiling.
       - If NOT found (PRIVATE company -- the common case for niche
         B2B markets), falls back to an LLM estimate from web
         snippets, with NO real ceiling.
     Then estimates per-country "coverage" (what % of each country's
     market the named companies represent) and grosses up to a full
     country total, summed to a grand total.
     REAL RELIABILITY ISSUE FOUND: for a market where 0% of companies
     have real financial data (e.g. avocado oil -- mostly private
     processors), the SAME --discover command run back-to-back gave
     318.6M, then 737.0M, then 585.4M -- a 2x+ swing on identical
     inputs. This is why it's opt-in, not default.

Both techniques can run together via --method both, printed side by
side and compared against the demand-side number (looked up from
generation_history.jsonl, or passed via --demand-value).

------------------------------------------------------------------
4. ME WORKBOOK PIPELINE (src/me_engine/{assembly,domain,io,curve}/)
------------------------------------------------------------------
Entry point: run_pipeline.py --input <Input Sheet.xlsx> --output <ME.xlsx>
Completely separate codebase from the demand-side generation above --
this takes an ALREADY-GENERATED Input Sheet (from step 2, or a human-
authored one) and turns it into the polished multi-sheet ME workbook.

Flow:
  WorkbookInspector   -> reads the Input Sheet's actual structure
                         (extracts real column/row layout).
  RuntimeTaxonomy     -> builds the schema IN MEMORY from what was
                         just read (no static schemas/*.json files --
                         works for any market's Input Sheet shape).
  Gate 1              -> validates the Input Sheet against that
                         taxonomy BEFORE any agent runs (fails fast on
                         a malformed input).
  Agents (Curve +      -> Curve agent: per-geography, does its own
    Segmentation+ASP)     fresh evidence gathering (ddgs again, per
                         country -- visible in logs as "[EvidenceAgent]
                         Germany: DDG: 3 queries -> 6 snippets -> 2
                         passed brain filter") and re-derives the
                         year-by-year curve. This is WHY the ME
                         workbook's number can differ from the Input
                         Sheet's number -- it's an independent re-
                         estimation, not a copy.
  Assembler           -> pure math: builds the full MarketResult from
                         all agents' outputs.
  Gate 3              -> validates the OUTPUT: identity checks (does
                         every number reconcile internally -- e.g. do
                         segment shares sum to the region total).
                         Real run: 9,454 identity checks, all passed.
                         Optional --reference: diffs against a known-
                         good human-built ME workbook, cell by cell.
  MEWorkbookWriter     -> writes the final .xlsx.

Output: an ME workbook .xlsx in agentGeneratedMEWorkbook/.

------------------------------------------------------------------
5. QUALITY / SANITY FLAGS (production-readiness layer)
------------------------------------------------------------------
Added specifically because bugs kept slipping through as confident-
looking wrong numbers (real example: "Global Watch Market" once came
back valued at $3M due to an unverified DB match pulling in a wrong
report's categories). Two flag modules:

  generation/quality.py (demand-side):
    - implausible_market_size  -- global value outside $10M-$5T
    - ungrounded_market_size   -- no real cited figure was found
    - low_confidence           -- reviewer score below 70%
    - no_evidence_found        -- no DB match AND no web results at all

  supply/quality.py (supply-side):
    - no_real_data             -- evidence-based found zero real figures
    - low_extraction_yield     -- <40% of relevant snippets yielded a
                                  real number (real bug this caught:
                                  "Global Cloud Computing Market" came
                                  out ~2x too low, 4/12 snippets
                                  extracted, before this threshold was
                                  tightened from an initial 30%)
    - small_sample             -- fewer than 5 real figures in the median
    - no_hard_capped_data      -- 0% of companies had real financial data
    - disagrees_with_demand_side -- >40% gap between two methods'
                                  totals for the same market

Surfaced in: backend SSE log + JSON summary, generation_history.jsonl,
compare_demand_supply.py CLI output + saved JSON report, and a warning
banner in the Next.js UI (right above the metric cards).

------------------------------------------------------------------
6. REAL DATA SOURCES USED (and what each actually does)
------------------------------------------------------------------
  Neon DB (Postgres)   -- our own library of past CMI market reports.
                          Keyword + semantic (embedding) lookup.
  ddgs (Python lib)     -- multi-backend live web search (Bing, Google,
                          Mojeek, DuckDuckGo with fallback). Replaced a
                          broken raw-DuckDuckGo-HTML scraper that was
                          failing with ConnectTimeout. Used independ-
                          ently by BOTH demand-side and supply-side
                          (not shared code, same library).
  sentence-transformers -- embedding model (all-MiniLM-L6-v2) for
                          vector/meaning-based relevance filtering.
  yfinance              -- free, unofficial Yahoo Finance wrapper --
                          real filed revenue for PUBLIC companies only.
  InsightSentry (RapidAPI) -- richer real financial data (revenue by
                          region, by business line) for public
                          companies that yfinance confirms first.
  Google Trends (pytrends) -- real public search-interest data, used
                          only as a small CAGR nudge, never the size.
  DeepSeek (LLM)        -- the actual "AI" doing every LLM call
                          throughout (OpenAI-compatible API).

WHERE THE WEB SEARCH RESULTS ACTUALLY COME FROM: mostly other market-
research firms' published report pages (Grand View Research,
Precedence Research, Mordor Intelligence, Fact.MR, Straits Research,
sometimes our own competitors' listings) -- NOT a curated IMF/World
Bank/Reuters feed. There isn't one plugged in; it's live search
ranking, whatever comes back for the query.

------------------------------------------------------------------
7. WHY THE AI IS STILL INVOLVED EVEN WITH REAL DATA
------------------------------------------------------------------
Real search results rarely hand over one clean, ready-to-use number:
  - Different firms disagree (real example: "Coffee Market" estimates
    ranged $74B to $489B depending on defined scope).
  - Articles cite a different target year than the one needed.
  - Nothing published gives the fine country/segment/price breakdown
    a client actually needs -- that table has to be built from the
    total.
  - Sometimes no explicit figure exists in what was found at all --
    the system still has to produce something, honestly flagged
    "ungrounded" rather than left blank.
The AI's real job is reconciling and filling those gaps -- it does
NOT get to override a real number when one is clearly, explicitly
stated. Code forces the AI's draft to match the real cited figure
when one exists (the $214M -> $214,000M correction is the concrete
proof this is enforced in code, not just prompted).

10. OPEN ITEMS / KNOWN LIMITATIONS (not solved yet)
------------------------------------------------------------------
- Run-to-run variance on the company-based supply-side method for
  private-company-heavy markets (no fix built yet -- idea: run N
  times, report median + spread instead of one-shot).
- Demand-side generation via source="db" hard-fails for any market
  with zero DB coverage -- no web-only fallback skeleton builder yet.
- No automated "golden set" regression test (a fixed list of markets
  with known real figures, re-run automatically on every code change
  to catch accuracy regressions before a client sees them).
- Accuracy/closeness tuning itself is explicitly the mentor's call,
  not something to keep iterating on in code alone.
- Input Sheet vs ME workbook drift (~6% seen on Avocado Oil) is
  expected by design (two independent re-derivations) but not yet
  explicitly bounded/flagged anywhere -- currently just a fact you
  have to know, not something the system calls out itself.

Confidence = 0.4 × Consistency + 0.6 × Plausibility

Consistency  = "Does the math actually add up?"  do all the segment shares in every group sum to 100%, and do the regional shares sum to 100
Plausibility = "Does this look like a realistic split for this market?"


Step 10 — Workbook Inspector. Pure deterministic code opens the Input Sheet and reads its actual real structure: 
how many rows/columns, which years are covered, how many geographies, how many segment dimensions. No assumptions — it
reads what's literally in the file.

"Runtime Taxonomy" = "the classification structure for this specific market, built fresh 
from the actual Input Sheet, not from a fixed template."

Step 11 — Runtime Taxonomy. Also deterministic. Takes those raw facts just read and builds a structured schema in
memory — not from a hardcoded template, from this specific file. This schema becomes the reference every following 
step checks against.

Step 12 — Validation Gate 1. Deterministic, no AI. Checks the Input Sheet's structure, segments, products, countries, 
and years all actually match what Runtime Taxonomy just built. Fails fast here if something's broken, before wasting 
any real LLM calls building on a bad foundation.

Step 13 — Curve Agent. Now the AI starts working, one country at a time. It starts from a deterministic baseline growth 
shape (derived from real markets, not invented), and only adjusts it — never sets an absolute dollar number. If it's 
unsure, it fires a real live web search for that specific country before deciding again. Deterministic code then 
validates the shape is smooth and realistic before accepting it.

Step 14 — Segmentation Agent (ME side). The AI sets a tiny yearly growth premium per segment (e.g. +0.4%/yr) — never a 
share directly. Deterministic code (a "Share-Drift Builder") compounds those tiny premiums into the actual year-by-year 
percentage-share path. The AI's real job here is small; the math is 100% code.

Step 15 — ASP Agent (ME side). Same pattern: the AI picks a yearly price-growth rate (e.g. 0.85%/yr), and deterministic 
code compounds that rate from the base-year price into the full 2021–2033 price path.

Step 16 — Assembler. Zero AI. Pure arithmetic: takes the Curve Agent's growth paths, the Segmentation Agent's share 
paths, and the ASP Agent's price paths — all already deterministic numbers by this point — and multiplies/combines them 
into one complete model: Market Value, Market Volume, and ASP, for every geography, every segment, every year.

Step 17 — Validation Gate 2. Deterministic again. Runs identity checks across the entire assembled workbook — do totals 
reconcile across sheets, do segment shares sum correctly, do geography sums add up. A real run: 9,454 checks, all passed. 
If a known-good reference file was supplied, it also diffs cell-by-cell against that.

Step 18 — ME Workbook Writer. Deterministic code writes the final multi-sheet .xlsx — 37 sheets, years 2021–2033, 
Market Value / Volume / ASP all in one file. This is the number that gets compared against the Input Sheet's number 
(real example: $748.3M vs $792.76M, ~6% apart — expected, since it was rebuilt independently, not copied).

Final screen — everything's ready to hand off: the Input Sheet, the ME Workbook, a JSON export of either, and any 
reports.

So the honest shape of the whole second pipeline: 3 deterministic steps → AI reasoning (small, bounded, always 
evidence-first) → 1 more deterministic step → 2 more deterministic steps. The AI only touches 3 of these 10 steps, and even there it never outputs the final number directly — code always does the actual math from what the AI decided.
